Why this was hard before

Shared Postgres alone was not enough

  • Sessions lived in memory — Authentication and user sessions sat primarily in embedded Infinispan.
  • Sticky sessions or XSite — Multi-DC meant affinity at the LB or Infinispan cross-site replication.
  • Failover broke mid-login — Another site did not hold the in-memory state the request needed.
  • Different route hostnames — Per-cluster routes created different OIDC issuers and broke clients after failover.

What made multi-cluster v2 possible

Three shifts — all required together

1
Persist critical state
Cross-site session-related state is externalized so another site can read it from storage.
2
Cache stays local
Embedded cache is per site (cluster-a / cluster-b) — not the multi-site source of truth.
3
One public issuer
Same hostname on every CR plus LB /lb-check so clients never care which CRC answers.

Necessary

Shared writable DB + stateless feature

Not sufficient alone

DB without stateless, or stateless without a consistent shared DB

Working scenario — drop a site

Interactive: traffic follows /lb-check

Mode: both sites healthy · round-robin

Packets only reach healthy backends. One site down = IdP continues on the other. Both down = complete sites failure (no auth until a site recovers).

DR questions — RTO and RPO

Two different clocks — do not conflate them

RTO
Recovery time objective — how long until the IdP (or DB) is usable again
RPO
Recovery point objective — how much committed data you can afford to lose
Failure mode Lab RTO* Lab RPO* What actually recovers
One Keycloak site down (peer UP, DB primary UP) ~15–30 s ~0 HAProxy /lb-check removes the dead site; issuer unchanged
Site A CRC down; Postgres + HAProxy still up ~15–30 s ~0 Same as above if Site B Keycloak is healthy
Both Keycloak sites down Until a site returns ~0 (DB intact) Complete sites failure — LB has nowhere to send OIDC
Postgres primary lost (need standby promote) Minutes (manual) ~0 if sync Promote standby, retarget JDBC, restart Keycloak — separate runbook

*Lab observations, not contractual SLOs. HAProxy check: inter 5s, fall 3 ≈ ~15s detection. Sync standby RPO assumes sync_state=sync.

DR scenario playbook

Answer the room before they ask

“What is our IdP RTO?”
For a single-site Keycloak outage with the other site healthy: dominated by LB health detection (seconds), not a full rebuild.
Prove it: drop one site in the SPA drill
“What is our RPO?”
With sync replication to the standby, committed transactions wait for the standby — RPO approaches zero for DB loss. Async would widen RPO.
Prove it: check pg_stat_replication sync_state
“Both sites failed — now what?”
That is complete sites failure. HAProxy cannot invent capacity. Restore at least one Keycloak — RTO is operational, not automatic.
Demo: Drop both sites on the canvas
“Did we lose the database?”
Different path: promote the sync standby, point both CRs at the new primary, restart pods. IdP site failover ≠ DB promote.
Runbook: scripts/promote-standby.sh

Sound bite: Multi-cluster stateless buys fast IdP RTO across sites. Sync Postgres buys low RPO for DB DR. Neither replaces the other.

Takeaways

What to carry forward

Same public hostname everywhere
Every Keycloak CR must advertise the LB URL as hostname/issuer — not per-cluster OpenShift route names.
Action: verify issuer after each deploy
Health check is the cutover signal
Probe GET /lb-check and expect UP. That is how a dead site leaves rotation without sticky sessions.
Action: wire LB checks before app traffic
Separate IdP RTO from DB RPO
Site failover is seconds via LB. Database promote is a manual DR path with its own clock.
Action: document both runbooks and targets
Both sites down is different
Complete sites failure is not covered by HAProxy alone — capacity must return somewhere.
Action: plan rebuild / spare capacity
